# 🛡️ LogicHive 概念的要件定義書

## ビジョン
**「過去の優れた実装を二度と書き直さない。良質なロジックをAIエージェントの共有知へ。」**

LogicHiveは、「どのように実装するか」という技術的な解決策ではなく、エンジニアが「どのような思想で自らの資産を管理すべきか」を定義するためのツールです。

---

## 🎯 実装方針: 何を何で行い、何を何で行わないのか

### 実装するもの (What We Implement)

| 対象 | 技術・手段 | 根拠 |
|---|---|---|
| **コードの保管** | SQLite + ChromaDB | 軽量、インフラ不要、個人ツールに最適 |
| **検索** | ベクトル検索 + キーワード検索 (Hybrid) | セマンティック検索と正確な名前検索の両立 |
| **品質ゲート (静的)** | AST解析 + ruff + セキュリティ監査 | 決定論的、再現可能、誰が見ても同じ結果 |
| **品質ゲート (AI)** | Gemini API | コードの「匂い」(設計の不自然さ等)を検出 |
| **MCPサーバー** | FastMCP + SSE Transport | Cursor/Claude等との統合、ネットワーク経由接続 |
| **防腐 (Anti-Rot)** | 定期的な再スコアリング | 劣化の検知と信頼スコアの自動調整 |
| **診断** | `check_integrity` ツール | DB・ベクターストアの整合性を一括自己検証 |
| **配布** | PyInstaller (.exe) + OCI Container | Windows互換性 + クラウドネイティブ |
| **実行検証** | Docker + venv + subprocess | MVP段階で素早く実装。隔離環境で安全にコードを実行 |

### 実装しないもの (What We Don't Implement)

| 対象 | 理由 |
|---|---|
| **ゼロからのコード生成** | エージェント(Cursor等)のLLMの方が常に賢い。生成は委ね、保存と再利用に徹する |
| **LogicHive側でのLLMによるコード解釈** | 利用側のエージェントが搭載しているLLMの方が最新。サーバー側でのメタデータ付与は「害悪なノイズ」 |
| **自動自己修復 (Self-Healing)** | エージェントの方が賢いため、サーバー側での勝手な修復は思考を妨げるノイズ。検知とスコアリングのみ |
| **汎用・巨大なライブラリ** | あらゆるケースに対応する重厚長大なヘルパーは保守コストが高い |
| **UI/UXのプレミアム化** | 個人ツールに不要。開発時間は検索精度や用户体验の改善に振り向ける |
| **全言語の自前パーサー** | Pythonのみ静的解析で品質を守り、他言語はLLMの推論能力に依存する「割り切り」 |

## ✨ 求めるもの (Seeking)

ほしいのはきれいなコードではなく、使える有用なコードを保存しておくことで、次の開発の際に楽にするです。

1. **「多言語原子」の再利用**:
   特定の文脈で完璧に動作したロジックだけを「原子」として蓄積し、瞬時に再利用する。
   対応言語: Python > HTML > CSS > その他。PythonとHTML(UI構築)があれば大概の開発が可能。

2. **エージェントとの「対話的」な適応**:
   AIは「生成者」ではなく、自分の資産の「適合者(Adapter)」として扱う。

3. **「知の資産化」による開発体験の向上**:
   書けば書くほど、自分の開発環境が強化される状態。

4. **ソフトウェアの「防腐(Anti-Rot)」と価値の維持**:
   保存した瞬間から劣化が始まる。LogicHiveの真の価値は「そのコードが今も動くのか」を自動で監視し、劣化を検知して信頼スコアを調整する「動的安定化」にある。

5. **「レジリエンス(弾力性)」と自己診断**:
   - 非同期・非ブロッキング: サーバーの応答性を常に維持
   - 例外の完全封じ込め: 致命的エラーでもサーバープロセスを道連れにしない
   - 統合診断ツール: DB、ベクターストアの整合性を一括で自己検証

6. **「動作保証の分離」**:
   MCPサーバー（ローカル）とVerification Server（遠隔）を分離し、検証ロジックの障害がMCPサーバー・DBに波及しない設計。

## 🚫 あきらめるもの (Giving up)

LogicHiveを運用するにあたり、私たちは以下のことをあきらめます。

1. **「記憶」への依存**: 「以前どこかで書いたはず」という不確かな記憶に頼る時間をあきらめる。
2. **「ゼロ」からのコード生成への期待**: AIが常に完璧なコードをゼロから生成してくれることを期待するのをあきらめる。
3. **「LogicHive側でのLLMによるコード解釈(お節介な加工)」**: サーバー側でLLMを使ってソースコードの依存関係を抽出しようなどという「善意の加工」を禁じる。
4. **「自動自己修復(Self-Healing)」**: 環境の変化に合わせてロジックを自動的に修正・修復する機能の実装を禁じる。劣化の「検知」と「スコアリング」には徹するが、「修復」はエージェントの知能に委ねる。
5. **「汎用・巨大」なライブラリの肥大化**: あらゆるケースに対応した重厚長大なヘルパークラスやライブラリを保守し続ける手間。
6. **UI/UXのプレミアム化**: 個人で利用するものに不要。
7. **全言語における自前の静的解析**: Pythonのみ静的解析で品質を守り、他言語はLLMに依存する「割り切り」。

## 🔄 コア・アルゴリズム(活用フロー)

LogicHiveとAIエージェント(Cursor等)は、以下のサイクルで協調します。

1. **Request (探索)**: 開発者がCursor上で「〜する処理が欲しい」とLogicHive MCPにリクエストする。
2. **Retrieve & Inject (抽出と挿入)**: LogicHiveが過去の「良質な関数」を検索し、一時的なファイル、あるいはクリップボードに書き出す。
3. **Adaptation (微調整)**: Cursorが、書き出された関数を「現在のプロジェクトの変数名や型」に適合するように自動的に微調整する。
4. **Static Validation (静的検証)**: 保存時に、決定論的指標(AST解析、ruff、セキュリティ監査)およびAI解析により品質を判定する。
5. **Execution Validation (実行検証)**: Docker + venv + subprocessで実際にコードを実行し、テストがパスすることを確認する。
6. **Registration (再登録)**: 微調整を経てさらに洗練された、あるいは新しく生まれた良質な関数を、再びLogicHiveに登録し、資産をアップデートする。

## 🏛️ 品質ゲートの設計原則:「意見」から「論理」への転換

### なぜこの節が存在するのか

LogicHiveの「防腐(Anti-Rot)」機構を構築する過程で、我々は重大な設計上の誤りを犯し、それを是正した。
この節は、その失敗と是正の記録である。同じ過ちを繰り返さないために、**なぜLLMのみによる品質判定が「論理」ではなく「屁理屈(Sophistry)」であったか**を明記する。

### 失敗の経緯:モグラ叩きの3ラウンド

**Round 1: 「テストを要求すれば良い」**
- 施策: テストコードの提出を必須化し、AIに「テストが十分か」を判定させた。
- 結果: `assert True` のような無意味なテストでも、AIは「テストが存在する」という事実に引きずられ、高得点を与えた。
- 敗因: AIは「テストの存在」と「テストの価値」を区別できなかった。

**Round 2: 「AIを厳しくすれば良い」**
- 施策: AIのペルソナを「Senior Architect」から「Hostile Forensic Auditor」へ変更し、AIスコアが低い場合に最終スコアを強制的に叩き落とす「Veto Power(拒否権)」を導入した。
- 結果: 完全に空のコード(`pass`メソッド)は検出できるようになった。しかし、**ビット演算やメタクラスで「1+1の計算」を過剰に複雑化した偽装コード**に対しては、AIが「ロジック自体は正しい」と判断し、45点という中途半端な温情を与えた。
- 敗因: AIは「技術的正しさ」と「実用的価値」を区別できなかった。

**Round 3: 「閾値をもっと上げれば良い」**
- 施策: 45点以下を強制的に0点に丸める「Score Binarization(二値化)」を計画した。
- 結果: この施策は「なぜ45点ではだめなのか」に対して「閾値を60にしたから」としか答えられない、恣意的なパラメータ調整であった。

**Round 4: 「厳格すぎて使われない」 (ドッグフーディングによる是正)**
- 現象: 品質ゲートが「ブラックボックス」かつ「完璧主義」すぎたため、開発のスピード感が阻害され、ユーザーが登録を躊躇する事態が発生した。
- 敗因: 失敗の理由(Tracebackやstderr)を隠蔽していたこと、および「テストがない＝悪」と決めつけていたこと。
- 教訓: **「厳格な番人」である前に、「親切な整備士」でなければならない。**

### 根本原因の特定

**「単一のLLM呼び出しに品質判定を委ねること」自体が、論理的に破綻している。**

| 「論理」に必要な性質 | LLMのみの品質判定 | 判定 |
| :--- | :--- | :--- |
| **再現性** (同じ入力に同じ結果) | 非決定的。同じコードでも実行ごとにスコアが変動する | 不適格 |
| **検証可能性** (第三者が根拠を確認できる) | 「AIがそう言った」以外の根拠がない | 不適格 |
| **決定論性** (数学的・構造的に結果が導かれる) | プロンプトの文言次第で結果が変わる | 不適格 |

### 是正方針:決定論的検証レイヤーの導入

**原則: 「事実(Fact)」が判定し、「意見(Opinion)」は補助する。**

- **Layer 1: 決定論的検証** - AST解析、ruff、セキュリティ監査、保守性メトリクス。再現可能、検証可能、決定論的。
- **Layer 1.5: 実行時検証** - Docker + venv + subprocessによるコード実行。隔離環境で安全にテストを実行。
- **Layer 2: AI補助検証** - LLMによるセマンティック分析。非決定的だが、有用な参考情報。最終スコアへの影響は補助的。

## 🏛️ 補足:エージェント賢者パラドックスと「整備士」の哲学

### 問い:エージェントが賢いなら、なぜこれほど厳しい検品が必要なのか?

**「エージェントが賢い操縦士だからこそ、渡される部品(VLU)は100%の純度を持つ『鋼』でなければならない。」**

1.  **知能の浪費を防ぐ**: エージェントが「このコードは本当に動くのか?」を確認したり、微細なバグを修正したりすることに知能のリソースを割くのは「損失」。
2.  **確実な基盤(Ground Truth)の提供**: エージェントが自信を持ってプロジェクトを推進するためには、背後に「絶対に嘘をつかない、厳格な整備士」が必要。
3.  **不純物の排除**: 「自分で直せるから、壊れていてもいい」という甘えは、資産の劣化を加速させる。

私たちは、エージェントを信じないから検品するのではありません。**エージェントの知能を「修正」という低次の作業から解放し、より高次な「創造」へと集中させるため**に、冷徹で厳格な門番(Gatekeeper)であり続けるのです。

## 📋 技術選択のまとめ

### 使うもの
- SQLite: ローカルDB
- ChromaDB: ベクトル検索
- FastMCP: MCPサーバー
- Gemini API: AI解析・埋め込み生成
- ruff: Python静的解析
- AST: Python構文解析
- PyInstaller: Windows配布
- OCI Container: クラウド配布
- Docker: 実行検証環境（隔離されたサンドボックス）
- venv + subprocess: Docker内でのコード実行

### 使わないもの
- 自前パーサー: 保守コストが高い
- UIフレームワーク: 個人ツールに不要
- 自動修復: エージェントの知能に委ねる
- ゼロからの生成: エージェントのLLMに委ねる
