# AI時代にコードが「腐る」のを防ぐ。決定論的品質ゲートを備えたロジック管理ハブ「LogicHive」を作った話

## はじめに
近年、CursorやClaude Desktop、WindsurfといったAIエージェントの進化により、私たちのコード生成速度は数十倍に跳ね上がりました。しかし、その裏で静かに、そして恐ろしい速度で進行している問題があります。

**「AIエージェントによるコードの乱造と、それに伴う技術負債の爆発的蓄積」** です。

AIは動くコードを数秒で吐き出しますが、そのコードにはしばしばテスト（アサーション）が欠落しており、動的環境での動作が検証されておらず、結果として「書いた瞬間から腐り始める（Rot）」という罠を抱えています。

この「AIによるコードの腐敗」に終止符を打ち、AIと人間が共創した高品質なロジックを組織や自己の「知の資産」として永続化するために、Model Context Protocol (MCP) 対応のロジック・ハブ **「LogicHive」** を開発しました。

本記事では、AIエージェントの温情主義を排する「決定論的品質ゲート（Rigor Gate）」の設計思想と、その実装について解説します。

---

## 1. 抱えていた課題：「AIの意見」は「論理」ではない

開発中にAIにコードを書かせ、それをそのままプロジェクトにマージし続けると、以下の3つの壁に直面します。

1. **AIの温情主義（非決定論的な評価）**:
   AIに「このコードの品質を監査して」と頼んでも、プロンプトの微細な変化やその時のモデルの状態によって評価スコアが乱高下します。AIはしばしば、テストコードが全くない空のメソッドや、極めて冗長なコードに対しても「文脈的には正しい」と40点や50点といった温情を与えてしまいます。
2. **コードの経年劣化（Bit Rot）**:
   ライブラリのアップデートやランタイムの変更により、かつて動いていたロジックはある日突然動かなくなります。AIエージェントは過去のコードが今も動くかを検証しないまま再利用しようとし、エラーを引き起こします。
3. **コンテキストの浪費（トークンコストの爆発）**:
   類似の実装を再利用させるために、毎回巨大なコードベースや過去のファイルをそのままAIのプロンプトにインプットすると、API費用が跳ね上がり、かつエージェントの思考能力（推論性能）が低下します。

これらの課題を解決するためには、AIの「主観的な意見」を排除し、**「数学的・客観的な事実（Fact）」でコードを検品する自動関門**が必要でした。

---

## 2. 解決策：Rigor Gate（決定論的ハイブリッド品質ゲート）

LogicHiveは、AIが生成したロジックを保存（Vault）する前に、4つのレイヤーからなる品質ゲートで厳格に検証します。

```
+-------------------------------------------------------+
|                 LogicHive Rigor Gate                  |
+-------------------------------------------------------+
|  [Fact Gate (40%)]      AST解析・アサーションの存在確認  |
|  [Static Gate (30%)]    Ruffによる静的解析、Radon複雑度  |
|  [AI Audit (20%)]       LLMによるセマンティック監査      |
|  [Execution (10%)]      隔離された動的環境での実行テスト  |
+-------------------------------------------------------+
```

### ① Fact Gate (事実の層: 40%) - 最も強い拒否権（Veto）
最も重要な転換は、**「正しさよりも検証可能性（Verifiability）を上に置く」**という設計です。
LogicHiveは、Pythonの `ast` モジュールを使用して抽象構文木を解析し、コード内に **`assert` 文またはテストコードがどれだけ存在するか** を物理的に数えます。
テストコードがないロジックや、中身が `pass` だけの空ロジック（Hollow logic）は、AIがどんなに「素晴らしいコードです」と主張しても、Fact Gateによって**強制的にリジェクト（拒否権発動）**されます。

### ② Static Gate (静的解析: 30%)
Ruffによる高速な静的チェックおよびRadonによる循環的複雑度（Cyclomatic Complexity）の計測を行います。これにより、AIが書きがちな「ネストが深すぎる複雑な関数」の保存を未然に防ぎます。

### ③ AI Audit (意見の層: 20%)
LLMによるコードの「匂い」の監査です。変数名が適切か、設計思想に不自然な点がないかをチェックします。ただし、AIの評価は非決定的であるため、スコア全体に占めるウェイトは20%と低く抑え、決定論的指標を揺るがさないようにしています。

### ④ Execution Gate (実行の層: 10%)
保存しようとするコードを、内部で一時的に構築する `uv venv` 仮想環境に送り込み、実際にテストスイートを実行します。動的にエラーを吐くコードは、この段階で弾かれます。

## 3. 重いライブラリ（PyTorch / Sklearn）を20秒で検証する技術

AI向けのロジックとして、`torch` や `scikit-learn` などをインポートする機械学習系のコードを保存したいケースがあります。しかし、検証のたびにこれらの重厚なライブラリを仮想環境にロードしていると、**20秒の品質ゲートタイムアウト**に引っかかります。

LogicHiveはこの課題を以下の2つのアプローチでクリアしています。

1. **Lazy Import（推奨）**:
   モジュールのトップレベルではなく、関数内部でインポートを実行させることで、初期のASTスキャン時におけるライブラリのロード遅延を回避します。
2. **Smart Mocking**:
   `save_function` のパラメータに `mock_imports` を指定することで、検証実行時に指定した重いモジュールを自動的に `MagicMock` に差し替えて実行し、環境依存による検証遅延をゼロにします。

## 4. Cursorに120秒で統合するクイックガイド

LogicHiveは、ネットワーク経由で複数の開発者や複数のクライアントから同時接続できるように、**Streamable HTTP (SSE)** アーキテクチャを採用しています。

Windows環境であれば、インストールの手間なく2分で接続できます。

### Step 1: EXEの起動
1. [LogicHive Releases](https://github.com/ayato-labs/LogicHive/releases) から最新の `LogicHive-MCP.exe` をダウンロードします。
2. コマンドプロンプト等で起動します。サーバーが `http://localhost:10880` で立ち上がります。

### Step 2: Cursorへの登録
1. Cursorの `Settings > Features > MCP` を開きます。
2. `+ Add New MCP Server` をクリックし、以下の通り入力して保存します。
   * **Name**: `logichive`
   * **Type**: `SSE`
   * **URL**: `http://localhost:10880/sse`

これだけで、CursorのAIエージェントが自動的にLogicHiveのMCPツールを認識し、過去に保存された検証済みロジック（Logic Atom）を探索・利用できるようになります。

## 5. ライセンスと今後のロードマップ

LogicHiveは、**AGPL-3.0**ライセンスの下でオープンソースとして公開されています。

*   **なぜAGPL-3.0なのか？**:
    この高品質な検証エンジンとロジック保管システムが、他社によって「ソースコードを非公開にしたまま有料SaaS」としてタダ乗りされるのを防ぎつつ、開発者コミュニティ全体が自由に改善し、フォークして独自の知のハブを立てられるようにするためです。
*   **ロードマップ**:
    現在はPythonに特化した `uv venv` サンドボックスですが、将来的にWebAssembly (WASM) や Firecracker (MicroVM) を用い、多言語（JavaScript, C++, Go等）で安全に隔離実行できる動的テスト環境の実装を計画しています。
